# ベンチマーク

[English](../benchmark.md) | 日本語

Registry はエージェントの書くものを変えるのか。1 つの画面、4 つの UI ライブラリ、3 つのホスト規模。
比較ごとの変数は「エージェントに何を見せるか」の 1 つだけとした。計測した実装は 60 — 可視条件と
規模の組で 36、Registry のみで 12、Screen JSON ルートで 8、実装への引き継ぎで 4。2026-08-13/14 に
計測、各セル 1 回、繰り返しなし。

ハーネス(ホスト、仕様、スクリプト、アームのプロンプト、生成された全画面)は別リポジトリとして
公開予定である。数値は方法への敵対的レビューが採点の欠陥を 2 件見つけたあとに一度訂正しており、
訂正内容とレビューの指摘はハーネスに同梱する。

## セットアップ

20 コンポーネントの合成プロダクト層(SNS タイムライン相当。投稿カード、コンポーザー、タブ、
パネル)を、共通の API 契約に従ってライブラリごとに 1 回ずつ、計 4 回実装した。対象は shadcn/ui
(Radix 1.2.6)、MUI 9.3.1、Chakra UI 3.36.1、Mantine 9.5.1。props のシグネチャは 4 ホストで同一
なので、違いはライブラリだけになる。この層は、育ったプロダクトがそうなるように各ライブラリから
乖離させてある。ドメイン enum(`visibility`、`tone`)を持つ。`size` ではなく `density`。バラの
props ではなく `post: PostModel`。children ではなく名前付きスロット。`onClick` ではなく
`onReplyPress`。20 個のシグネチャが全パッケージで一致することはスクリプトが検証する。React
19.2.8 と TypeScript 6.0.3 は 1 つのワークスペースルートに揃えた。

各アームはファイル読み取り・grep・シェルを持つ Claude(Opus 5)のエージェントで、ホストと採点
スクリプトを書いたのと同じモデルファミリーである。どのアームも同じ画面(投稿 4 件、引用、メディア、
サイドバーのパネル 2 つを持つタイムライン)を 1 つの `.stories.tsx` として書く。仕様はコンポーネント
名とデータを固定してある。どのアームも `node_modules` を持たないため、コンパイラを回しながら直す
ことはできない。最初に提出されたファイルを `tsc --noEmit` で採点し、スクリプトが仕様と突き合わせ、
レンダリングは Storybook で抜き取り確認する。

## 4 条件

各ホスト 20 コンポーネント時の、提出 Story の型エラー数(「クラッシュ」はレンダリング時の例外)。
Registry のみとソースありの条件は 80 / 240 コンポーネントでも実行し、該当する全実行がゼロだった
ため、表は何かが起きる唯一の規模を示している。

| ホスト | 仕様のみ | 仕様 + Registry | 仕様 + ソース | ソース + Registry |
| --- | --- | --- | --- | --- |
| shadcn/ui | 36、クラッシュ | 0 | 0 | 0 |
| MUI | 33、クラッシュ | 0 | 0 | 0 |
| Chakra UI | 26 | 0 | 0 | 0 |
| Mantine | 24 | 0 | 0 | 0 |

この表には 2 つの比較が入っていて、それぞれ別のことを言っている。

**情報ゼロと比べると、Registry は欠けていたもの、つまり API を供給する。** 仕様のみの条件は誰の
働き方でもない。他に何も無いとき Registry が何を足すかを切り分けるための条件である。この条件の
画面を精査すると、内容はほぼ正しい。引用、メディア、公開範囲、固定されたカウントは仕様と一致して
いる。間違っているのは API であり、それも派手に、4 ライブラリを通じて同じ形になる。名前付き
スロットを取るカードへの children。`post` モデル 1 つを取るコンポーネントへ渡されたバラの
`replyCount` / `liked`。`onReplyPress` に対する `onReply`。`label` に対する `timestamp`。意味は
仕様が供給していた。API は誰も供給していなかった。Registry はその欠けた半分である。
`component list` と `component inspect` の出力 12.5〜16KB で、同じ条件が 4 ライブラリすべてで
ゼロになる。80 / 240
コンポーネントでもゼロのままで、そこには `PostCardCompact` や `SearchBar` のような、実在の
コンポーネントと紛らわしい名前で props だけが異なるものを意図的に置いてある。Registry のみの
12 試行で、紛らわしい名前を選んだ例は一度も出なかった。これは、チェックアウトを持たない
リポジトリへ MCP 越しに向き合うときや、大きなホストをコンテキストから外すときに、エージェントが
実際に置かれる条件である。

**ソースを読めるエージェントと比べると、Registry は何も変えない。** ソースが見えるセルは全規模で
ゼロである。コンパイルが通る誤りも互角だった。片側 12 試行ずつで、ソース側の誤選択は 1 回
(`SearchField` の代わりに `SearchBar`。両ファイルを読み、警告も受けた上での選択)。Registry
併用側も 1 回である(`NotificationBell` の代わりに `IconActionButton`)。どちらのスロットも
`ReactNode` でコンパイルは通る。似た名前から選ぶのは判断であり、どの参照手段もそれを肩代わりしない。

**Registry の死角は描画の慣習である。** MUI だけは `PostAuthorLine` が handle に `@` を付けずに
そのまま描画する実装なので、正しいデータは MUI では `"@rin"`、他では `"rin"` になる。ソースを
読んだ MUI の 6 アームは全員正解した。Registry のみの MUI 3 アームのうち 2 つは `Rin Amano rin`
と表示される画面を出した。Registry が言えるのは `handle: string` までで、コンポーネントがそれを
どう描くかは言えない。コンパイルは通り、見た目が間違う。ソース無し条件が出した唯一の欠陥クラスが
これである(12 試行中 2 件)。この種の事実はソース、Story、スクリーンショットにしか無く、Registry
は運ばない。

## Registry を引くコスト

ソースを読める限り正確さは同点なので、差は読解量にある。以下は実際に読まれた量ではなくコーパスの
大きさで、正直な 3 列で示す。1 列目はコンポーネントディレクトリ全体(上限値。grep を使う
エージェントはこれより少なく読む)。2 列目は `*Props` インターフェイスブロックのみ(下限値。どこを
読めばよいかを最初から知っている前提)。3 列目は Registry(`component list` 全件 + 画面が使う 18
コンポーネント分の `component inspect`)。

| コンポーネント数 | ソース全読 | ソース props のみ | Registry |
| --- | ---: | ---: | ---: |
| 20 | 20〜27KB | 5.5〜6KB | 12.5〜16KB |
| 80 | 75〜110KB | 21〜27KB | 22〜25KB |
| 240 | 231〜332KB | 64〜80KB | 44〜49KB |

どちらの曲線もホスト規模に対して線形で、Registry は成長率ではなく係数が小さいだけである。狙い
読みの下限値と比べると、20 コンポーネントでは Registry の方が多く読み、80 で並び、240 で 3 分の
2 程度になる。正直なコスト主張は控えめで、デザインシステム規模で全読の 3〜5 分の 1。より強い形は
前の節の条件である。エージェントが読む必要のあるホストのコードはゼロにできる。ただし描画慣習の
死角という代価がつく。

## 残る 2 つの仕組み

**Screen JSON バリデーション。** 対象は静的画面(このルートが想定する種類の画面。今回のタイム
ラインは関数 props を必要とするため対象外になる)。静的画面では両ルートとも 4 ホストすべてで
クリーンな Story を生成し、JSON ルートは型検査なしで 2 往復のうちに収束した。エラーは正確である
(ノード指定つきで、正しい選択肢が列挙される)。ただし 2 つの但し書きが要る。捕まえたのはすべて
形式自体の摩擦(`schemaVersion` の欠落)だったこと。そしてバリデータ自身の最終出力が、`json` 型の
props は検査されずそのまま Story に書かれると明言していること。この画面の意味はまさにそこに
住んでいる。仕組みとしてのループは機能している。だがこの実験では意味検査層が何かを捕まえる姿は
示せなかった。上流の `component inspect` が、それが捕まえるはずの誤りを先に防いでいたからである。

**実装への引き継ぎ。** 承認済み Story から実際の状態を持つページへ、`story import` +
`screen context` の有無で比較すると、両側ともエラーゼロ、配線も完全だった。ただし配線の一覧は
仕様自身が列挙していたので、この同点は設計上の同点でもある。より重要な数字は別にある。この
ベンチマークの承認済み Story 24 本のうち 21 本は `component` + `args` 形式の CSF である。
`story import` はそれを読めない(`STORY_NOT_FOUND`。ドキュメント化されたフォールバックは Story
をテキストとして読むこと)。読めるのは `render` 形式(自身の `screen generate` が出力する形式)で、
そちらではツリーを忠実に復元した(28 ノード、fixtures 7 個)。

## この測定が示さないこと

- ホストは合成であり、乖離レシピはダイヤルである。仕様のみ条件のエラー数は、レシピが適用した
  改名の数の関数になる。レシピはハーネスと共に公開する。あの列は「この程度の乖離が生むもの」で
  あって定数ではない。
- 各セル 1 回、繰り返しなし。コンパイルが通る誤りの頻度(12 試行あたり 1〜2 件)は、追加の 1 回で
  どのセルも動き得る領域にある。
- 仕様がコンポーネント名とデータを固定しているため、どのコンポーネントを使うかをアームが決める
  場面はなかった。ワークフローの前半にあたる探索とキュレーションは未測定である。
- 240 コンポーネントは最大級のデザインシステムより 1 桁小さく、紛らわしい名前のファミリーは 220
  個中 20 個にとどまる。
- ホスト、フィラー、全画面、採点スクリプトのすべてを同じモデルファミリーが書いた。意味の検査は
  正規表現と的を絞った目視で、全数の人間レビューではない。

実コードでの抽出品質(props が型から取れた率、バレルインポートの慣習、抽出できないパターン)は
別の問いであり、実運用のデザインシステムで別に測定している:
[Component Registry](./registry.md)。
